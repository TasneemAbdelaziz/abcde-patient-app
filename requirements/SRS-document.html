1 · Introduction

1.1 Purpose

This document specifies the requirements for the A.B.C.D.E System, a patient-centered digital healthcare platform for Alamein Model Hospital. It defines what the system shall do, organized by subsystem, with the feature set, the actors who use each subsystem, the data exchanged, current build status, and the source of each requirement. It is the shared reference for the development team, the hospital stakeholders, and the quality reviewers.

1.2 Scope

A.B.C.D.E covers the journey of a hospital patient — with a primary focus on the acute myocardial infarction (heart-attack) pathway — from arrival through triage, diagnosis, cardiac catheterization, recovery, admission, discharge, and home follow-up. The platform has three faces:

  • Patient mobile app — journey tracking, AI advisor, medication, appointments, reports, family access, feedback, indoor navigation, and accessibility.
  • Public web portal — hospital information, departments, doctors, news, and appointment requests for visitors without an account.
  • Staff web dashboards — for doctors, nursing, reception, family, quality, administration, and emergency response.

The system works alongside the hospital's existing DMS (Data Management System) rather than replacing it. The current release is a clickable patient-app prototype; staff dashboards, AI engines, indoor navigation, accessibility, and DMS integration are specified here but not yet built.

2 · Overall Description

2.1 Product Perspective

A.B.C.D.E is an additive layer over the hospital's current digital infrastructure. The IT department confirmed:

  • The hospital runs DMS as its primary HMIS; the Laboratory is fully integrated with DMS.
  • Radiology uses a separate system (named "Milestone" during the visit — to confirm with IT).
  • The Pharmacy is connected to DMS but partly manual.
  • The hospital does not currently own integration APIs; they can be purchased from the DMS vendor.
  • All departments communicate over a hospital Local Area Network (LAN).
  • Medical devices are not connected to the system — only Radiology and Labs are.
Implication: the integration subsystem is built around DMS, an API catalog to be purchased, a LAN with IP-whitelisting and an external server, and API documentation with dummy data for development. Vitals are entered manually (no device feed), and early-warning runs on manual vitals plus lab values.

2.2 Patient Journey & Arrival Pathways

Every patient is first assessed by a Head Nurse (Triage) and classified as:

  • Cold case — non-urgent; routed to the appropriate outpatient clinic (or reception outside clinic hours).
  • Emergency case — urgent; transferred to the Emergency Department.
  • Critical case — unconscious / accident / life-threatening; bypasses triage and goes directly to Emergency.

The journey is therefore a branching workflow, not a single linear timeline. Four arrival pathways were documented:

PathwayEntryKey behavior
1 · ER with familyTriage roomParallel: nurse records vitals while admin data is collected from patient/family. ER physician present in triage; refers to specialty (e.g., Cardiology).
2 · ER via ambulanceER room directlyRadio pre-alert is manual, not recorded; ambulance vitals are not trusted and re-measured in ER. Three parallel actions: ER exam · re-measure vitals · family registers.
3 · Outpatient (Cold)ReceptionIn-person booking only (no phone). Nurse records vitals before the clinic. Findings on specialty-specific paper forms, then entered to the system by IT.
4 · Operations (Cold)Operations scheduleRequires a prior exam at this hospital. Physical medical file created; surgeon writes the surgical requisition book; nurse computes the weekly Risk Score; a final financial file is issued at the end.

2.3 User Classes

The hospital's patients are largely local residents of Matrouh, members of nearby Arab tribes, and North-Coast workers — which makes a simple, multilingual, accessible interface essential. The system roles are:

PatientFamily / CaregiverGuest DoctorNurse / Nursing supervisorReceptionist Quality ManagerDepartment HeadHospital Director System / IT AdminThree-Doctor Committee

2.4 Constraints

  • Reception scope is administrative-only — reception never touches medical data.
  • Medical-file access is restricted to the treating doctor and the nursing supervisor; even family members may not view it. Each department (branch) sees only its own part of the patient's data.
  • No integration APIs exist today; the system must run as the primary source where DMS data is unavailable, and integrate once APIs are purchased.
  • Operates over the hospital LAN; performance and security tuned for that environment.

2.5 Assumptions & Dependencies

  • DMS vendor APIs will be procured to enable read/write integration.
  • Radiology system identity ("Milestone") and the third pharmacy location are pending IT confirmation.
  • Anonymized real-case validation and hospital/ethics approvals are obtained before live piloting.

3.4

Patient Journey & Care Coordination

In prototypeReceptionistNurseDoctorPatientFamily

Purpose: track the patient through every stage of the visit on one shared ticket.

  • 4.1Open a visit ticket on arrival (ticket no., starting stage, anonymized code).
  • 4.2Triage classification by head nurse: Cold / Emergency / Critical; Critical bypasses triage (Δ visit).
  • 4.3Branching stage engine supporting the 4 arrival pathways, not a single linear timeline (Δ visit).
  • 4.4Parallel arrival actions: record vitals while admin data is captured (Δ visit).
  • 4.5Cold-state operations track: physical file, surgical requisition book, weekly risk score, final financial file (Δ visit).
  • 4.6Stage ownership: each stage has a responsible staff member who advances the patient; alternate (exception) paths.
  • 4.7Patient-facing status text per stage (e.g., "Under assessment", "In procedure", "Stable").
  • 4.8Unidentified life-threatening path: when the case is life-threatening and no patient information is available, activate the Three-Doctor Emergency Committee to assess severity, confirm the emergency, approve immediate intervention, assume medical responsibility, generate a Direct Admission Form, and authorize immediate transfer to the Catheterization Unit (Δ visit).
  • 4.9Select catheterization type and route to the responsible specialist: cerebral → neurologist / neuro-interventionist, cardiac → cardiologist, peripheral → vascular surgeon; interventional radiology is future scope (Δ visit).
  • 4.10Post-procedure complications branch: route a procedure-related complication back to the doctor who performed the catheterization; otherwise raise a consult to the appropriate specialist (neurology / cardiology / vascular / ICU) (Δ visit).
  • 4.11Structured discharge step: record Condition at Discharge (Improved / Stable / Deceased) and recommendation (home / transfer), deliver Family Education (procedure outcome, medications, warning signs, follow-up), and book the weekly follow-up (or per doctor's recommendation) (Δ visit).
Reconcile: ambulance radio pre-alert and in-vehicle vitals are not recorded or trusted; vitals are re-measured in ER. The stage engine must reflect this.

Source: Q17, Q18, Q33–Q37 · Reception & catheterization docs.

6 · Data & Forms Model

The records subsystem (§3.7) is built on the documented clinical artifacts:

  • Patient File Record (11 sections): basic info · admission/discharge summary · personal history · internal-transport safety (RSTP) · daily antibiotics · medication prescription & administration · multidisciplinary care plan · nutritional care plan · VTE/Padua risk assessment · doctor's orders · consultation request.
  • Clinic diagnosis forms: Dental examination + informed consent (form code SMC-F-ALH-008) · Gyn-Obstetric outpatient · Pediatric outpatient — each with patient data, history, examination, plan of care, investigations, medications, follow-up, referral.
  • Catheterization workflow: arrival → identification → catheterization type (cerebral / cardiac / peripheral / interventional radiology) → procedure → post-procedure → discharge → complications → treatment options; includes the Three-Doctor Emergency Committee.
  • Identity & insurance logic: Serial from National ID, arrival vs. booking cards, and the insurance decision tree (insured / employer / uninsured-capable / uninsured-unable → committee).
